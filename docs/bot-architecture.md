# План реализации ТЗ Telegram-бота (по этапам)

Основано на аудите (`docs/bot-audit.md`) и открытых вопросах
(`docs/QUESTIONS.md`). Список файлов — по существующим директориям
проекта, без новой структуры/monorepo.

## Этап 1a — безопасная часть, без бизнес-решений (эта сессия)

Ничего здесь не меняет видимое поведение бота для клиента и не требует
ответа на вопросы из `QUESTIONS.md`.

1. **Идемпотентность по `update_id`.**
   - Таблица `telegram_processed_updates(update_id bigint primary key,
     processed_at timestamp)`.
   - В `POST` вебхука: `INSERT ... ON CONFLICT DO NOTHING`, если 0 строк
     затронуто — Telegram уже прислал этот update, выйти без повторной
     обработки.
   - Файлы: `src/db/schema.ts`, `src/app/api/telegram/webhook/route.ts`.

2. **Атомарное «Взять в работу».**
   - Новая кнопка в `buildOrderCardKeyboard` (`telegram.ts`) — только на
     статусе `new_order` и пока `assignedManagerId is null`.
   - Реализация: `UPDATE requests SET assigned_manager_id = $1 WHERE id =
     $2 AND assigned_manager_id IS NULL RETURNING id` — если 0 строк,
     значит кто-то уже взял, ответить `answerCallbackQuery` с текстом
     «Уже взято в работу другим менеджером» и обновить карточку.
   - Файлы: `src/lib/order-bot.ts`, `src/lib/telegram.ts`,
     `src/app/api/telegram/webhook/route.ts`.

3. **Ранняя выдача публичного номера.**
   - Перенести вызов `nextOrderNumber()` из перехода в `in_production` в
     момент создания заявки (`submitRequest` в `src/lib/actions.ts` и
     `resolveNewOrderPrompt` в `order-bot.ts`).
   - Показывать номер в карточке заказа и клиенту сразу после отправки
     заявки (`request-form.tsx`, `wardrobe-configurator.tsx`).

Каждый пункт — отдельный коммит, после каждого: `npx tsc --noEmit`,
`npm run lint`, `npm run build`, ручная проверка на проде.

## Этап 1b — требует ответа на вопросы 2–4 (роли, регистрация, группа)

- Добавить `role` в `employees` (или отдельную таблицу `employee_roles`,
  если нужно несколько ролей на человека).
- Если подтверждено «администратор добавляет вручную» — экран в
  `/admin` для добавления Telegram ID сотрудника с ролью, без
  самостоятельной регистрации ботом. Иначе — оставить текущий
  self-service флоу «Я менеджер», но зафиксировать это как осознанное
  отклонение от ТЗ.
- Если подтверждён отказ от группового чата — переработать
  `postNewOrderCard`/`handleCallbackQuery`: карточки и кнопки уходят в
  личные чаты, а не в `TELEGRAM_STAFF_CHAT_ID`. Это затрагивает большую
  часть `order-bot.ts` и требует, чтобы у каждого сотрудника уже был
  привязан Telegram ID (то есть зависит от пункта выше).

## Этап 1c — клиентский профиль и привязка (требует ответа на вопрос 1)

- Если контакт-кнопка признана достаточной — формализовать уже
  работающий флоу как официальный `TelegramIdentity`-эквивалент,
  задокументировать, тестов на конфликт (см. `bot-audit.md` риски)
  добавить в первую очередь.
- Если нужен SMS OTP — отдельная работа: таблица `otp_challenges`,
  интеграция с выбранным провайдером, лимиты/cooldown из раздела 3 ТЗ.
  Не начинать без выбранного провайдера (спецификация прямо запрещает
  «фиктивную SMS-интеграцию»).

## Этап 2 — рабочий процесс продаж (раздел 4, 6 ТЗ)

Каталог из общей БД в боте, диалоги клиент–менеджер (новые таблицы
`conversations`/`conversation_messages`), SLA/эскалации, поиск и сводка
менеджера, вложения через существующий upload-слой
(`src/lib/upload-actions.ts`, уже есть локальное хранилище с валидацией
типа/размера — переиспользовать, а не создавать новый).

## Этап 3 — заказ и сервис (раздел 5, 7 ТЗ частично)

Отдельные сущности `Lead`/`Order`/`ServiceTicket` вместо одной таблицы
`requests` на все состояния — потребует миграции существующих заявок и
осторожного разделения `request_status` enum. Конфигурируемая таблица
переходов статуса вместо `DIRECT_ACTIONS` в коде, если бизнесу нужно
менять переходы без деплоя.

## RU/UZ и тесты — сквозные, отдельные треки

- **i18n**: с нуля (нет `next-intl` или аналога). Предложение —
  `next-intl` (совместим с App Router), словари в `messages/ru.json` /
  `messages/uz.json`, переключатель языка пишет в cookie/профиль
  клиента и `telegramPendingActions`-подобную запись для бота. Большой
  объём — переводить придётся отдельно каждый экран сайта и бота.
- **Тесты**: предложение — `vitest` (быстрее, ESM-нативный, хорошо
  работает с Next.js). Мокать Telegram API через `fetch`-мок на уровне
  модуля, БД — через тестовую ветку Neon (`neondb` поддерживает
  branching) или through-away Postgres в CI. Не подключать к
  продакшн-базе никогда.

## Что не делается без явного запроса

- Никаких миграций, которые переименовывают/дропают существующие
  колонки `requests`/`employees`/`customers` без явного подтверждения —
  только `ADD COLUMN`/новые таблицы, обратно совместимые с уже
  работающим кодом.
- Никакого отключения текущей группы `TELEGRAM_STAFF_CHAT_ID`, пока не
  подтверждён вопрос 4 — иначе живые менеджеры мгновенно потеряют канал
  получения заказов.
