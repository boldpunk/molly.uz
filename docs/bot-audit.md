# Аудит Telegram-бота Molly Home

Дата: 2026-09-18. Проведён перед реализацией технического задания
`MOLLY_BOT_TECHNICAL_SPEC_CLAUDE_CODE.md`. Ниже — что реально есть в
репозитории `boldpunk/molly.uz` на момент аудита, что можно переиспользовать,
и где спецификация расходится с текущей системой.

## Стек и расположение

- **Next.js 16** (App Router), TypeScript, Tailwind. Один репозиторий,
  без monorepo.
- **ORM**: Drizzle (`src/db/schema.ts`), драйвер `drizzle-orm/neon-http`
  поверх `@neondatabase/serverless`. **Важно**: `neon-http` не поддерживает
  `db.transaction()` — в кодовой базе нигде не используется. Многошаговые
  операции сейчас либо укладываются в один `UPDATE`, либо выполняются
  последовательно без отката.
- **СУБД**: Neon Postgres (продакшн — единственная ветка, без staging;
  `.env.local` указывает прямо на прод).
- **Бот**: webhook, не long polling. Точка входа —
  `src/app/api/telegram/webhook/route.ts`. Секрет проверяется через заголовок
  `x-telegram-bot-api-secret-token` (`TELEGRAM_WEBHOOK_SECRET`).
- **Бизнес-логика бота**: `src/lib/order-bot.ts` (мутации),
  `src/lib/telegram.ts` (низкоуровневые вызовы Telegram API, клавиатуры,
  форматирование карточки заказа), `src/lib/telegram-links.ts` (deep-link
  `p_<phone>`).
- **Деплой**: self-hosted на Hetzner, Docker + nginx, GitHub Actions как
  SSH-прокси (`deploy.yml` на пуш в `phase-1-storefront`). Веб-сайт и бот —
  один и тот же Next.js процесс; отдельного health-check эндпоинта нет.

## Модель данных (факт)

Таблицы в `src/db/schema.ts`, относящиеся к боту/заявкам:

| Таблица | Назначение | Соответствие ТЗ |
|---|---|---|
| `customers` | веб-аккаунт клиента (`phone` unique, `passwordHash`, `telegramId` unique, `telegramNotifyOptIn`) | частично `Customer` + `TelegramIdentity` — они слиты в одну таблицу, 1 Telegram-аккаунт на клиента |
| `employees` | **только** `telegramId` (unique) + `name`. Никакой роли, никакой связи с `admin_users` | сильно упрощённый `Employee` — нет `Role` |
| `admin_users` | веб-логин в `/admin`, роли `administrator/content_editor/catalog_manager/sales_manager` | это **вторая, отдельная** система ролей — она не привязана к Telegram и не используется ботом |
| `requests` | лид/заявка. Одно поле `status` (enum `request_status`), `statusHistory` jsonb, `orderNumber` (nullable, выдаётся только при переходе в `in_production`), `assignedManagerId → employees` | ближе всего к `Lead + Order`, слитым в одну сущность — нет разделения «заявка на замер» / «заказ» / «сервисное обращение» |
| `requestItems` | позиции заявки, снимок названия/slug на момент отправки | соответствует `RequestItem`, snapshot уже частично есть (название, но не цена/тип цены) |
| `telegramPendingActions` | key-value «что бот ждёт следующим сообщением» (`register_name`, `amount_deposit`, `amount_paid_full`, `new_order_entry`) — ближайший аналог FSM-состояния/`BotSession`, но не универсальный | зачаток `BotSession`, узкоспециализированный |
| `wardrobeFinishes` | не относится к боту (конфигуратор шкафа) | — |

Отсутствуют как отдельные сущности: `Role` (для Telegram-ролей),
`Conversation`/`ConversationMessage`, `ServiceTicket`, `Attachment`,
`Notification`/`NotificationDelivery`, `OtpChallenge`, `AuditLog`,
`FaqEntry`, `ProductSnapshot` (частично есть — только имя товара),
таблица допустимых переходов статуса, таблица идемпотентности `update_id`.

## Что уже фактически покрывает часть ТЗ

- **`p_<phone>` deep link уже существует и работает** ровно как описано в
  «Подтверждённом контексте» ТЗ: `src/lib/telegram-links.ts` строит
  `https://t.me/mollyhomeuzbot?start=p_<digits>`, обработчик — в
  `route.ts` (`/^\/start(?:@\w+)?(?:\s+(\S+))?\s*$/`). Полностью
  совместимо, ломать не нужно.
- **Безопасная привязка через `request_contact`** — уже реализована
  (`REQUEST_CONTACT_KEYBOARD`, `handleCustomerContact`). Это ровно тот
  «безопасный серверный способ», который ТЗ разрешает как альтернативу
  OTP по SMS (раздел 3: «Если этого недостаточно… отправить одноразовый
  код через уже подключённый SMS-провайдера» — **в проекте нет
  подключённого SMS-провайдера**, значит контакт-кнопка Telegram
  (проверяется самим Telegram, что номер принадлежит отправителю) —
  единственный доступный сейчас «безопасный серверный способ»).
- **История статусов с автором и временем** — `statusHistory` jsonb на
  каждой заявке, пишется при любом изменении (`appendHistory` в
  `order-bot.ts`). Не отдельная таблица, но данные те же.
- **Разрешённые переходы статуса** — не таблица конфигурации, но и не
  «произвольная строка»: `DIRECT_ACTIONS` + `backTarget()` в
  `telegram.ts` жёстко перечисляют допустимые действия и целевые статусы.
  Подделать переход можно только если подделать сам `callback_data`,
  который проверяется (`parseCallbackData`, формат `a:<uuid>:<action>`).
- **Секрет вебхука проверяется.**
- **Только сотрудники из группы могут менять статус** —
  `handleCallbackQuery` сверяет `chat.id` с `TELEGRAM_STAFF_CHAT_ID` перед
  выполнением любого действия над заявкой.
- **Только что исправлено в этой же сессии** (до получения этого ТЗ):
  явный выбор роли «Я клиент / Я менеджер» вместо угадывания по
  свободному тексту (см. историю коммитов) — частично закрывает пункт
  «Меню и явное подтверждение», но полноценного меню менеджера/клиента
  по ролям из раздела 4/3 ТЗ ещё нет.

## Критические расхождения с ТЗ (не мелочи)

1. **RU/UZ билингвальность отсутствует полностью.** В шапке сайта есть
   статичная надпись «RU / UZ», но переключателя языка, файлов переводов
   или `i18n`-библиотеки в проекте нет (`grep` на `next-intl`/`i18n`
   ничего не находит, кроме двух нерелевантных совпадений). Все тексты
   бота и сайта — на русском, захардкожены в JSX/строках. Полное
   покрытие UZ для каждого экрана (акцептанс-критерий №9 ТЗ) — это
   отдельный, большой пласт работы (перевод +架构 переключения языка),
   а не часть «фундамента».
2. **Нет тестовой инфраструктуры вообще.** Ни `vitest`, ни `jest`, ни
   единого `*.test.*` файла в репозитории. Раздел 12 ТЗ требует unit +
   integration + e2e + security-тесты в CI — это отдельная настройка
   (выбор фреймворка, мок Telegram API, мок БД или тестовая ветка Neon)
   поверх уже написанного кода.
3. **Нет очереди/фоновых заданий.** Вебхук обрабатывает всё синхронно в
   рамках HTTP-запроса (`route.ts` → `await handleMessage/...`). Нет
   retry с backoff — `callTelegramApi` при ошибке просто логирует и
   возвращает `null` (это и стало причиной недавнего бага с «тихо
   переставшими приходить» уведомлениями в этой же сессии). ТЗ требует
   dead-letter/очередь — в проекте нет ни Redis, ни какой-либо очереди,
   значит либо реализовывать на таблице БД (poor man's queue), либо
   явно зафиксировать отклонение.
4. **Нет идемпотентности по `update_id`.** Telegram может повторно
   доставить один и тот же update. Сейчас ничего не мешает дважды
   создать карточку заказа или дважды применить одно действие менеджера
   при повторе. Это прямой пункт критериев приёмки (№10) — и лёгкая,
   безопасная часть работы, которую стоит закрыть в первую очередь.
5. **Нет атомарного «Взять в работу».** Сейчас `assignedManagerId`
   переписывается на автора *любого* действия последним пишущим —
   без явной кнопки захвата и без защиты от гонки: если два менеджера
   одновременно нажмут разные кнопки на одной устаревшей карточке,
   выиграет тот, чей `UPDATE` пришёл последним, без предупреждения.
   Нужна отдельная кнопка + условный `UPDATE ... WHERE assigned_manager_id
   IS NULL` (или аналог, раз транзакций нет).
6. **Публичный номер заказа выдаётся поздно.** `orderNumber` сейчас
   генерируется только при переходе в `in_production` (`nextOrderNumber()`
   в `order-bot.ts`), а не сразу при создании заявки, как требует раздел 3
   ТЗ («присвоить понятный публичный номер… после создания»).
7. **Роли Telegram-сотрудников не существуют.** `employees` — плоская
   таблица без `role`. Модель ТЗ (клиент / менеджер / старший менеджер /
   администратор, раздел 2) не на чем строить без новой колонки/таблицы
   и **без решения**, кто именно назначает роль сотруднику (сейчас *любой*,
   кто напишет боту и нажмёт «Я менеджер», становится «сотрудником» —
   это прямо противоречит ТЗ: «Telegram user ID сотрудника должен быть
   заранее добавлен администратором… самостоятельное получение роли
   запрещено»). Это находится в проекте с самого начала сессии, не
   регрессия только что внесённого фикса.
8. **Диалоги, сервисные обращения, FAQ, отзывы, аналитика** — не
   реализованы вообще, весь раздел 3 (кроме заявки на замер и каталога)
   и раздел 4 (кроме карточки лида) — с нуля.
9. **Audit log отсутствует.** Есть только `statusHistory` на заявках —
   не покрывает вход сотрудника, просмотр контактов, изменение прав и
   т.д. (раздел 9 ТЗ).
10. **Снимок товара в заявке неполный.** `requestItems` хранит имя,
    slug, но не цену/тип цены на момент отправки — при изменении цены в
    каталоге старая заявка не отражает то, что видел клиент.

## Риски специфичные для *этого* проекта

- **Это уже живой продакшн с реальными клиентами** (в рамках этой же
  сессии была видна живая переписка настоящего клиента с ботом). Любая
  миграция схемы или смена ключевой логики (`registerEmployeeName`,
  `handleCallbackQuery`, формат `callback_data`) должна быть обратно
  совместима либо выкатываться без разрыва текущих диалогов.
- **Нет staging-окружения бота.** Есть только одна база (прод) и один
  деплой-пайплайн на прод-сервер. Тестировать новый FSM/OTP-флоу
  придётся либо на отдельной ветке Neon с отдельным ботом
  (`getUpdates`/тестовый токен), либо очень осторожно на проде.
- **`employees` уже содержит реальные записи** (два реальных менеджера)
  без ролей — миграция на модель с ролями должна проставить им роль по
  умолчанию, не сбросив доступ.
- **Группа сотрудников `TELEGRAM_STAFF_CHAT_ID`** — единственный канал,
  куда сейчас падают карточки новых заказов и по которому определяется
  «кто сотрудник» для действий. ТЗ прямо рекомендует уйти от группового
  чата к персональной авторизованной работе (раздел 9: «не отправлять
  персональные данные в групповой чат менеджеров, если нет строгой
  необходимости») — это меняет основной канал уведомлений, на который
  сейчас всё завязано.

## Вывод и что дальше

Спецификация описывает полноценный CRM/тикет-портал: OTP-аутентификацию,
FSM с конфигурируемыми переходами, диалоги, сервисные тикеты, аудит-лог,
SLA-эскалации, две параллельные системы ролей, объединённые в одну, и
полный RU/UZ билингвизм с тестами на каждый экран. Это на несколько
порядков больше кода, чем весь текущий бот (`order-bot.ts` +
`telegram.ts` + `route.ts` — around 900 строк), и затрагивает
продакшн-базу живого бизнеса.

Реализовать это безопасно одним проходом без промежуточной сверки с
владельцем продукта — рискованно: часть решений (SMS-провайдер, нужна ли
реально роль «старший менеджер» отдельно от «менеджера» прямо сейчас,
приоритет UZ-перевода, отказ от группового чата в пользу личных
уведомлений) влияет на то, что вообще стоит строить в первую очередь.

Открытые вопросы зафиксированы в `docs/QUESTIONS.md`. План по этапам —
в `docs/bot-architecture.md`.
