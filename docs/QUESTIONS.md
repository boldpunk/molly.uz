# Открытые вопросы по ТЗ Telegram-бота — решения

Технический аудит — в `docs/bot-audit.md`. По просьбе владельца продукта
решения приняты без дополнительного согласования — консервативно, в
пользу минимального разрушения уже работающего процесса живых
сотрудников. Если что-то из этого не подходит — можно пересмотреть в
любой момент, ничего необратимого не сделано.

1. **SMS-провайдер для OTP.** Решено: **не подключать SMS.** В проекте
   нет ни одного SMS-шлюза, а завести его — это отдельная бизнес-
   и инфраструктурная задача (выбор провайдера, договор, стоимость).
   Уже работающая привязка через Telegram-кнопку «поделиться контактом»
   — это ровно тот «безопасный серверный способ», который ТЗ прямо
   разрешает как альтернативу (раздел 3): номер подтверждается самим
   Telegram, подделать нельзя через обычный UI бота. Оставляем как есть.

2. **Роль «Старший менеджер».** Решено: **не вводить пока.** Сейчас
   реально работают два сотрудника без явной ролевой модели. Отдельная
   роль «старший менеджер» (переназначение, возврат статуса, просмотр
   аналитики) добавит сложность, которая пока не нужна — если появится
   такая необходимость, добавить роль в `employees` тривиально
   (колонка уже задумана расширяемой, см. пункт 3).

3. **Кто добавляет сотрудника.** Решено: **да, переходим на
   подтверждение администратором** — это единственный пункт из
   вопросов, который является реальной дырой безопасности прямо
   сейчас: любой, кто напишет боту «Я менеджер» и укажет имя, до этого
   момента сразу попадал в список получателей уведомлений о новых
   заказах (с именем, телефоном и комментарием клиента). Реализовано в
   этой же сессии: заявка на регистрацию сотрудника теперь попадает в
   очередь на подтверждение в `/admin/employees` (только для роли
   `administrator`), а не сразу становится полноценным сотрудником.
   Действия в группе (кнопки статусов) не менялись — они и раньше были
   защищены членством в закрытой группе, а не таблицей `employees`.

4. **Групповой чат сотрудников.** Решено: **оставить как есть.** ТЗ
   рекомендует уйти от группы к личным уведомлениям, но менеджеры прямо
   сейчас работают через группу «Molly - сайт», и в этой же сессии
   только что был восстановлен пайплайн уведомлений в неё. Менять
   основной рабочий канал сразу после того, как его почитили —
   неоправданный риск. Личные уведомления о новых заказах (DM) уже
   дублируются каждому подтверждённому сотруднику — этого достаточно
   как страховка на случай проблем с группой, без отказа от неё.

5. **Приоритет UZ-перевода.** Решено: **отложить.** Переключатель
   «RU / UZ» в шапке сайта декоративный — переводов нет ни на сайте, ни
   в боте. Это отдельный большой объём работы (перевести каждый экран),
   не относящийся к структуре и надёжности бота. Делается отдельной
   задачей, когда будет явный запрос.

6. **Тестовая инфраструктура.** Решено: **отдельный трек, не блокирует
   текущую работу.** В проекте нет ни одного теста и нет staging-
   окружения для бота (одна база — прод). Каждое изменение в этой
   сессии вместо автотестов проверяется вручную: `npx tsc --noEmit`,
   `npm run lint`, `npm run build`, и живая проверка на проде (через
   Playwright-скриншоты, тестовые заявки/действия с последующей
   очисткой). Заводить `vitest` и мок-слои для Telegram API — отдельная
   задача, когда объём кода бота оправдает содержание тестов.

7. **Порядок этапов.** Решено: **следовать порядку из ТЗ** (Этап 1 —
   фундамент, Этап 2 — диалоги и SLA, Этап 3 — заказ и сервис). Более
   срочных отклонений не поступало.

Что это меняет прямо сейчас: реализовано подтверждение сотрудников
администратором (пункт 3) — единственное решение из списка, требующее
кода. Остальное либо уже соответствует ТЗ (пункт 1), либо сознательно
отложено (пункты 2, 4, 5, 6), либо не требует действия (пункт 7).
